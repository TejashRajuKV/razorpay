3. END-TO-END DATA FLOW

Payment/failed payment
  → detection:        backend/src/services/recoveryService.detectRevenueAtRisk()       (SQL query)
  → risk prediction:  backend/src/services/mlService.predictRisk() → ml app.py /predict/risk  (sklearn or heuristic fallback)
  → diagnosis:        backend/src/services.mlService.diagnose() → ml app.py /predict/diagnosis  (sklearn or rule fallback)
  → recovery decision: backend/src/services.recoveryService.decideBestSafeAction()  (EV ranking + guardrails)
  → guardrails:      checkStoppingRules() — resolved/stopped, retry limits, cooldown, high-value+low-conf, low prob
  → timing:          timingService.recommendTiming()  (failure reason + attempts + hour + success rate)
  → profile:         customerProfileService.getCustomerRecoveryProfile()  (advisory, used for channel/incentive)
  → incentive:       incentiveService.recommendIncentive()  (tiers, net-recovery compare)
  → channel:         channelService.recommendChannel()  (action+reason+amount+history→channel)
  → message:         messageService.generateMessage()  (template interpolated from case values)
  → simulated recovery: simulatorService.executeAction()  (mock success/failure with recoveredAmount)
  → outcome:         outcomeFeedbackService.recordOutcome()  (stores to ml_predictions for future adjustment)
  → ROI/analytics:   roiService.calculateROI() + advancedAnalyticsService.getAdvancedAnalytics()  (post-run aggregates)
  → audit:           auditService.logEvent()  (immutable event log for every stage)

5. SAFETY / GUARDRAILS (from actual code)

  • resolved/stopped cases cannot recover again — checkStoppingRules() returns {allowed:false} for both statuses
  • retry limits — MAX_RETRY_ATTEMPTS=3 enforced in checkStoppingRules via getCurrentAttemptCount + getTotalAttemptCount
  • retry cooldown — checked via last retry action's cooldown_until timestamp; active cooldown blocks retry
  • total recovery attempt limits — MAX_RECOVERY_ATTEMPTS=5 enforced globally per case
  • high-value + low-confidence escalation — amount > HIGH_VALUE_THRESHOLD (50000) AND confidence < LOW_CONFIDENCE_THRESHOLD (0.40) → forces 'escalate' action; humanEscalation=true in guardrails
  • blocked actions create audit records — every safety_check_blocked event logged with entity_type='action', event_type='safety_check_blocked'
  • STOP_RECOVERY really stops — Dashboard + executeRecoveryAction both return {success:false, blocked:true} for action='stop'; status set to 'stopped'/'resolved' never reverts
  • Channel/message features cannot bypass guardrails — channel/recommendChannel and generateMessage are purely descriptive; decision flow still runs checkStoppingRules before any recommendation

6. ML INTEGRATION

  • Backend connects to Python ML service via ML_SERVICE_URL=http://localhost:5000 (from .env.example, also backend .env fallback)
  • Endpoints used: /predict/risk, /predict/diagnosis, /predict/recovery, /predict/batch, /evaluate/risk/diagnosis/recovery
  • Fallback behavior: if ML service unreachable → axios catch → return heuristic fallback predictions (risk: baseRate+reasonModifier; diagnosis: REASON_DIAGNOSIS_MAP; recovery: base rates + history/segment adjustment)
  • NO external AI/LLM APIs — all local sklearn or deterministic rule-based heuristics
  • Application operates fully if Python ML is unavailable — all decisions fall back to local models; guardrails independent of ML availability
